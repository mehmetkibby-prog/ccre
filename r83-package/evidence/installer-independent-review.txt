Startup and database protections retained
-----------------------------------------
- Actual live release root, service command/configuration, original core identity,
  complete release manifest, R82 HTTP identity, inherited SQL timing/checkpoint
  modules and pinned Node runtime are validated before applying the delta.
- The installer permits application only in the existing closed/preregistration
  or completed-maintenance states and requires no active presence, recent players
  or admissions. It does not silently authorize opening the game.
- Account service identity and database descriptor are tracked throughout. The
  service wrapper explicitly forbids stopping the accounts service.
- Installation mutex and actual configured daily-backup mutex are both held.
  The environment/configuration binding is rechecked after waiting for the lock.
- The game service is stopped and every process holding its database inode must
  be gone before code overlay. Guards prevent ordinary service restart while a
  partial active update is journaled.
- The backup opens the live game database mode=ro and uses SQLite's backup API,
  including committed WAL. It verifies quick_check and fsyncs a private backup.
  That backup is a precaution; neither apply nor rollback copies it over the live
  database. No database inode replacement or migration is in the reviewed call path.
- Code writes use fsynced temporary files and same-filesystem atomic replacement,
  rechecking the before hash immediately before replacement. An unexpected edited
  destination, parent symlink or code backup hash causes refusal.
- Four ready channels, durable state, expected realm DB identity, pinned runtime,
  and R83 diagnostics/version must pass before the update can finish.
- On failure, gameplay is fenced/stopped even if guard creation fails. Recovery
  restores only original code and prior STATE metadata, then verifies the restored
  release and health. Account service/data and the current game DB are preserved.

Recovery scope
--------------
validate_expanded_record reconstructs the expected five entries using the exact
payload and original release manifest/install-operations bytes, obtained either
from their known live before hash or indexed verified code backup. The journal
cannot supply an extra path, asset hardlink, different backup slot, or new cleanup
directory. Original and target core identities must match the recomputed plan.

The recovery record must belong to this R83 package/plan, source root, services,
database descriptor, configuration and startup drop-in. A partial R82 record is
not adopted. RuntimePlan permits validation only; it contains no runtime delta.

Manual rollback after gameplay has progressed takes a new precautionary database
backup and preserves current database contents. It never restores an old DB copy.
Validated completion/cleanup failures remain resumable instead of unnecessarily
rolling back already healthy code. Cleanup removes only the private backup whose
inode/size were recorded; incomplete unverified backups are not silently restored.

Scope of confidence
-------------------
The source and payload checks support the narrow patch and preservation claims.
They do not establish live-VDS filesystem space, service state, load, final public
download integrity or live gameplay behavior. Those are checked by the installer's
preflight/health gates or by subsequent operational observation.
